# Writing a docs page

For pages under `docs/content/docs/`. `AGENTS.md` at the repo root says what belongs
there: everything a person writing a layout file needs, and nothing about how Tauler is
built inside.

`pnpm run check:pages` (`docs/scripts/check-pages.mjs`, part of `pnpm run checks`)
enforces the parts of this file marked **checked**.

## Every page

- `description` is one sentence with no colon in it. A colon there once broke the
  front-matter parse. **Checked.**
- The title states what the reader wants to do, as an action: "Read a value from an
  external program", not "Streams". A formal name appears in the body, never in the
  title.
- Facts, not adjectives. "Tauler" is capitalised. Headings are imperative.
- Every example runs against fields and programs that exist. If an example needs a
  program, the page prints the program. Evaluate each example before you commit it (see
  [Checking examples](#checking-examples)).
- A `<panel>` in an example has an `id`, a `width` and a `height`. A layout without them
  does not load.
- Link only to pages of this site and to public URLs.

## The article template

A page opts in with `template: article` in its front matter. Pages in
`content/docs/data/` and `content/docs/interaction/` must name a template, except
`index`. **Checked.**

```
---
title: <the need, as an action>
description: <one sentence, no colon>
template: article
---

<1-2 sentences: what the reader gets, then the concept's formal name in bold, once.>

<the smallest example that runs as written, about 10 lines of layout>

## How it works
<4-5 sentences. The model. No API details.>

## Common tasks
### <imperative heading>
<one sentence, then one example. Repeat per task.>

## Rules
**<The constraint, as a full sentence.>** <Why it exists, or what happens otherwise.>

## Reference
### `signature(args)`
<arguments table, then the return value>
### Behaviour
- **Before the first value.** …
- **When it updates.** …
- **On errors.** …
- **On a reload.** …

## Related
- [Link](/docs/…): a few words on why the reader would go there.
```

The five `##` headings are fixed, in that order, with no others. A part may be one line
but is never missing. **Checked:** the five headings, an example and a bold term before
the first heading, at least one task, and `### Behaviour` under Reference.

## The shipped-service template

For a page about one program that ships with Tauler (`tauler-i3`, `tauler-notify`).
Opt in with `template: service`.

```
<what the program does, and that a layout uses it as a service>
<a complete layout that uses it>
## Install
## State it prints        <a sample line, then a table of fields>
## Events it accepts      <a table: the dispatch call, the effect>
## <anything else the program needs explained>
## Related
```

**Checked:** the first three headings, and `Related` last.

## Vocabulary for dynamic data and interaction

`CONTEXT.md` is the glossary. On user pages these are the only names:

| Name | Meaning |
|---|---|
| subprocess | a program Tauler runs |
| stream | a subprocess the layout reads (`useStringStream`, `useJSONStream`), or a built-in one such as `tauler:outputs` |
| event | `{ type, ... }`, one line of JSON on the program's stdin |
| dispatch | sending an event (`useDispatch`); a verb, there is no noun for the program |
| service | a subprocess the layout reads and dispatches to (`useService`) |
| store | state the layout owns (`store`): shared at the top level of a file, local inside a component |
| screen | a connected monitor |

- Do not write intent, channel, actor, message, command or module in the prose of a
  templated page. What a dispatch call returns is "an event addressed to that program";
  a handler takes a list of them. **Checked** (code is not).
- `useEvents` and `<Module>` are earlier names. Each is mentioned once, in the Reference
  part of the page that replaces it, as "the earlier name, still works".
- Say that the layout "runs again". State lives in another program or in the layout; the
  layout keeps nothing between runs.
- Lead with analogies that hold on every platform: a program that reads and writes lines
  of JSON, `postMessage`, React's `useReducer`. Readers come from macOS and from the web
  as well as from Linux bars.
- The interaction pages build on the dynamic-data pages, never the other way round.

## Checking examples

There is no way to show a live result on a hand-written page: the live examples on the
component reference are generated by `tauler-docgen` from doc comments, and
`tauler-screenshot` runs no streams. So check that each example evaluates:

- A complete layout: `tauler-screenshot --input example.jsx --output /dev/null` evaluates
  it with every stream empty, which also proves the guards for the first run.
- A program: run it in a terminal and type the lines Tauler would write, starting with
  the startup event from `content/docs/data/programs.md`.

## Moving a page

The site is a static export, so a moved URL needs a stub. Add the old path to `MOVED` in
`src/app/docs/[[...slug]]/page.tsx`. Anchors cannot be redirected: fix every inbound
link.
